# JEV Fund

## Overview

JEV Fund is a transparent, tax-funded Polymarket trading project. Trading fees generated by a token launched on Flap are collected in a designated tax wallet, converted to USDC, and deposited into a public Polymarket account. The account uses JEV market decisions plus deterministic risk rules to trade BTC Up or Down five-minute markets. Resolved principal and profit or loss remain in the account and affect the size of subsequent positions.

The product is designed as a public treasury rather than a user-facing trading terminal. Its primary job is to make capital origin, strategy behavior, open exposure, historical performance, and execution evidence understandable and verifiable.

## What is JEV?

JEV is TypeSafe's first public System One Model. TypeSafe describes it as a model built for decisions inside software: an application sends structured state and receives typed decisions, probabilities, and confidence values.

JEV is not used as an unrestricted wallet operator. In this project it performs one bounded task: estimate whether BTC is more likely to finish UP or DOWN relative to the active Polymarket five-minute window.

The surrounding application remains responsible for:

- validating input freshness and completeness;
- checking the confidence threshold;
- comparing estimated probability with the executable market price;
- enforcing maximum price, timing, and duplicate-trade rules;
- calculating position size;
- submitting or rejecting an order;
- recording execution and settlement.

This separation matters: JEV produces a probabilistic opinion, while deterministic code controls money and execution.

## Capital lifecycle

1. A token is launched through Flap with trading tax enabled.
2. Trading tax is sent to the published tax wallet.
3. Collected tokens are converted to USDC.
4. USDC is deposited into the published Polymarket account.
5. The agent reads the current account balance and active market state.
6. JEV returns an UP/DOWN probability and confidence.
7. Deterministic policy decides whether the signal may be traded.
8. A valid order is sized from the current available balance.
9. Position, decision summary, order identifier, and execution proof are published.
10. Resolution proceeds return principal and profit or loss to the same account.
11. The next order is sized from the updated balance.

Tax conversion and Polymarket funding may initially be manual. Automating that transfer is not required for the first release.

## Position sizing

The target stake is approximately one fiftieth of available Polymarket balance:

```text
target_order_usd = available_balance_usdc / 50
```

Examples:

| Available balance | Target stake |
| ---: | ---: |
| $250 | $5 |
| $300 | $6 |
| $500 | $10 |
| $1,000 | $20 |

The target is not automatically executable. The engine must calculate shares from the current ask and satisfy Polymarket's current minimum order and minimum share rules. Five shares do not always cost five dollars.

## Decision policy

The current strategy evaluates approximately every five seconds:

1. Load the active BTC five-minute market and BTC spot context.
2. Ask JEV for side, probabilities, and confidence.
3. Reject stale or incomplete inputs.
4. Reject confidence at or below the configured threshold.
5. Reject an ask above the maximum permitted price.
6. Reject a signal without sufficient probability edge over the ask.
7. Reject entries too close to market resolution.
8. Reject duplicate entries or excess trades for the same window.
9. Calculate the balance-based stake and validate market minimums.
10. Submit once and hold to resolution when all checks pass.

## Public website

The website is split into four routes:

- `/` — treasury overview, capital loop, official accounts, and public wallets;
- `/positions` — current market, open position, live pricing, and JEV decision summary;
- `/history` — resolved and open trade ledger with P&L and execution evidence;
- `/about` — JEV explanation, system architecture, methodology, and transparency policy.

The site reserves visible locations for:

- official X/Twitter account;
- official Polymarket profile;
- Flap tax wallet;
- Polymarket funding/account address.

Unknown accounts must be shown as **Not configured**. Placeholder addresses and transactions must be labeled **Demo** and must never be presented as real proof.

## JEV decision transparency

For every decision, the public interface should show:

- observable market context;
- UP and DOWN probabilities;
- confidence;
- policy threshold results;
- sizing inputs and final stake;
- final action: BUY UP, BUY DOWN, WAIT, or HOLD.

The site publishes structured decision summaries, not private model chain-of-thought. This provides useful auditability without fabricating hidden reasoning.

## Data states

Every value must be assigned one of these states:

- **LIVE** — retrieved from a real external source;
- **PAPER** — generated by simulated execution against live or fixture data;
- **DEMO** — fabricated solely for interface development;
- **ONCHAIN** — supported by a valid public transaction or wallet record;
- **PENDING** — awaiting execution, confirmation, or settlement.

At the current development stage, market data and JEV decisions are live through TeamO Router, orders are paper trades, and account balances, history, wallet addresses, and transaction hashes are demo placeholders.

## Production integration order

1. Configure the TypeSafe/JEV API key.
2. Connect the public Polymarket account in read-only mode.
3. Replace demo balance, positions, activity, and history.
4. Store real order identifiers and execution evidence.
5. Implement secure signer and secret management.
6. Validate the full system in paper mode.
7. Enable tightly limited live execution.
8. Connect Flap tax-wallet accounting.
9. Optionally automate token conversion and Polymarket funding.

## Risk and disclosures

- JEV probabilities are estimates and can be wrong.
- Prediction-market prices can move before an order fills.
- Minimum order rules and market APIs can change.
- Tax collection does not guarantee trading profit.
- Wallet access, signing keys, and automated transfers create security risk.
- The website must not imply that demo results are historical performance.
- The project is experimental software and not financial advice.
